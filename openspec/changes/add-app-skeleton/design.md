# Design

## Context

Greenfield-репозиторий: базовая спека зафиксирована, кода нет. Технологические ограничения заданы vision: Electron с тонким рендерером, типизированный IPC, SQLite, полностью локальная работа, CI-сборки под Windows/macOS/Linux. Реализуемые требования: `desktop-platform` (4 требования) и базовая часть `ui-shell`.

## Goals / Non-Goals

**Goals:**
- Запускаемый каркас приложения, на который будут надстраиваться доменные этапы без перестройки инфраструктуры.
- Зафиксировать паттерны, которым последуют все будущие change: IPC-мост, Repository над ORM, миграции, темы, хоткеи.
- Поднять CI с полной матрицей артефактов с первого дня.

**Non-Goals:**
- Доменная функциональность: партии, замеры, расчёты, глоссарий, экспорт JSON — последующие change.
- Полный WCAG-аудит: закладываем дизайн-токены контраста, аудит — при появлении реальных экранов.
- Индикация длительных операций: паттерн (состояние загрузки в Zustand) без реальных длинных операций.

## Decisions

### D1. Бойлерплейт и упаковка: electron-vite + electron-builder
Дев-сборка через `electron-vite` (HMR для renderer, TS из коробки), релизная упаковка через `electron-builder`.
*Почему не Electron Forge*: Forge — официальный тулчейн Electron и взвешивался всерьёз (главный козырь — официальность и один инструмент на всё), но его core-makers не покрывают матрицу артефактов спеки: ни `deb`, ни `tar.gz`. `tar.gz` ещё можно репакнуть из zip, но `deb` репаком не получить — понадобились бы community-makers или самописная обёртка fpm в CI, то есть собственный инфраструктурный код на поддержке. electron-builder выдаёт всю матрицу нативно: NSIS `.exe`, macOS `.zip`/`.dmg` (arm64, x64, universal), `.deb`, `tar.gz`.
*Бонус на будущее*: auto-update осознанно вне скоупа vision, но при добавлении `electron-updater` работает на тех же артефактах electron-builder (`latest.yml` генерируется той же сборкой) — выбор не запирает эту дверь. Оговорка: на Linux self-update возможен только в формате AppImage, не в `deb`/`tar.gz`.

### D2. Рендерер: React + TypeScript + Zustand
Vision требует «React + StateManager» без имени. Выбор — Zustand: минимальный бойлерплейт, TypeScript-first, хватает для локального стора.
*Альтернативы*: Redux Toolkit (тяжелее для десктоп-масштаба), Jotai (атомарная модель избыточна).

### D3. IPC-мост: invoke/handle + zod на границе
- Каналы описываются дескрипторами в `src/shared/ipc/`: типы запроса/ответа + zod-схемы рядом (единый источник типов из vision).
- Main-сторона регистрирует handler с валидацией запроса; renderer получает ответ валидированным.
- Обёртка `invoke` с таймаутом и нормализованной ошибкой (`code`, `message`).
- Пуш-события от бэкенда — типизированный контракт в `src/shared/events/` (не сырой `ipcRenderer.on`).
- `send/on` не используется для запросов — только для пушей.
- Renderer изолирован: `contextIsolation: true`, `nodeIntegration: false`, `sandbox: true`; доступ только через тонкий preload-мост (`contextBridge.exposeInMainWorld`).

### D4. Хранилище: better-sqlite3 + Drizzle ORM
- Drizzle даёт типизированные запросы и генерацию миграций (`drizzle-kit`) без рантайм-оверхеда; репозитории — тонкие классы над drizzle (паттерн Repository из vision).
- *Альтернативы*: TypeORM (декораторы, тяжёл), Prisma (движки и генерация клиента — тяжело для десктопа), Kysely (типизированный «Knex», но миграции вручную), Knex (зрел и стабилен, типы строк передаются generic'ом вручную и со временем расходятся со схемой; async-API не даёт выгоды над синхронным better-sqlite3 в main-процессе — SQLite однопоточен).
- Режим WAL включается pragma при открытии; БД — `app.getPath('userData')/winemaker.db`.
- Все временные метки — ISO-8601 UTC (TEXT): читаемо в будущем JSON-экспорте.

### D5. Миграции и автобэкап
- Миграции применяются при старте main-процесса, транзакционно, с записью версии схемы в таблицу `__schema`.
- Перед применением миграции создаётся копия файла БД (`better-sqlite3 .backup()`).
- Регулярный бэкап: при старте + по интервалу при наличии изменений + при корректном выходе; ротация последних 5 копий в `userData/backups/`. Асинхронно, вне блокирующего пути.

### D6. SingleInstance и локальность
`app.requestSingleInstanceLock()`: повторный запуск активирует существующее окно вместо нового экземпляра. Strict CSP в `BrowserWindow`, все ресурсы локальные, никаких сетевых вызовов в коде.

### D7. Темы, клавиатура, масштабирование
- Темы: CSS custom properties + атрибут `[data-theme]`; дефолт по `prefers-color-scheme`, переключение сохраняется в БД (`app_state`).
- Клавиатура: центральный хук хоткеев в renderer, roving tabindex для списков; шорткаты объявляются декларативно в одном месте.
- Масштабирование: типографика на `rem`, верстка без фиксированных пиксельных размеров; проверка на 100/125/150 % — чеклистом в tasks.

### D8. Состояние представления
Таблица `app_state (key TEXT PK, value JSON)` + репозиторий. Скелет сохраняет: тему, размеры/позицию окна. Будущие экраны допишут свои ключи без изменения инфраструктуры.

### D9. Utility Process (заготовка)
Протокол общения через `MessagePort` описывается типами в `src/shared/utility/`; в скелете — спавн-модуль и эхо-проверка. Реальные вычисления (пересчёты, пакетная обработка) подключат доменные этапы.

### D10. CI: GitHub Actions
Матрица: `windows-latest`, `macos-latest` (arm64 + universal), `ubuntu-latest`. Шаги: vitest → electron-builder (`--publish never`) → upload артефактов. Запуск на PR (тесты + сборка без публикации) и на тегах `v*`.

## Risks / Trade-offs

- [Нативный модуль better-sqlite3 требует сборки под ABI Electron] → пин версий, prebuilt binaries, проверка `electron-builder install-app-deps` в postinstall; сборка всех платформ проверяется в CI с первого дня.
- [Два инструмента: electron-vite + electron-builder] → возможны несовпадения версий; фиксируем проверенную пару в package.json и проверяем релизную сборку локально до CI.
- [Universal-сборка macOS удваивает время CI] → допустимо; при необходимости переключаемся на раздельные arm64/x64 артефакты без изменения спеки (она допускает оба варианта).
- [Бэкап по интервалу может потерять последние минуты при сбое] → WAL переживает аварийное завершение самого приложения; бэкап страхует отказ диска/миграций. Интервал — константа, подберём на практике.
- [Миграции при старте блокируют запуск] → на скелете схемы минимальны; при росте — фоновое применение с экраном-заглушкой.
- [macOS предупреждает: приложение «не откроется на следующей версии macOS» (28)] → причина подтверждена логом сборки: «skipped macOS application code signing — cannot find valid Developer ID Application identity» — артефакты собираются ad-hoc подписанными, без нотаризации. Apple делает подпись Developer ID + нотаризацию обязательными для будущих macOS. Для локального личного использования не горит (запуск через «Открыть» в контекстном меню / Privacy & Security). Перед распространением на другие машины или переходом на macOS 28: Apple Developer Program ($99/год), сертификат Developer ID Application, включение подписи и нотаризации в electron-builder (identity в keychain + `mac.notarize`), секреты — в GitHub Actions. Смена версии Electron не лечит предупреждение (45.5.0 — актуальный мажор), но держать Electron свежим нужно отдельно: Apple деградирует SDK, собранные старыми тулчейнами.
- [Будущий auto-update требует сети и конфликтует с требованием `desktop-platform` «Полностью локальная работа»] → отложено из vision осознанно; при добавлении — отдельный change с MODIFIED-требованием (opt-in, явно инициированная пользователем проверка обновлений). Технический путь уже открыт: electron-updater на тех же артефактах; главное затратное место — подпись кода и нотаризация macOS, а не механика обновления.

## Migration Plan

Greenfield — миграция продакшена не требуется. Откат первой версии: удаление `userData` (данных пользователя ещё нет). Бэкап перед миграцией закладывается сейчас, чтобы правило работало с первого релиза.

## Open Questions

- Точная палитра и дизайн-токены тем — при появлении реальных экранов; сейчас нейтральные токены-заготовки.
- Интервал периодического бэкапа (по умолчанию 5 минут) — подстроить на реальном сезоне.
- Финальный набор шорткеев — определится по мере добавления экранов; паттерн и реестр уже фиксированы.
