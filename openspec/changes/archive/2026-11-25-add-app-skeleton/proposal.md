# Proposal

## Why

Проект — greenfield: пока нет ни строчки кода, а вся базовая спека уже зафиксирована. Первый этап реализации — «ходячий скелет»: каркас приложения, поверх которого будут надстраиваться домены (партии → замеры → расчёты). Без него ни один домен нельзя даже начать.

## What Changes

- Создаётся каркас кросс-платформенного десктоп-приложения: главный и рендерер-процессы, типизированный IPC-мост с валидацией, общий каталог `shared/` для типов.
- Подключается SQLite-хранилище: версионированные миграции схемы, режим WAL, автоматический бэкап файла БД, временные метки в UTC.
- Включаются SingleInstance и гарантия полностью локальной работы (ни один экран не требует сети).
- Закладывается оболочка интерфейса: светлая и тёмная темы, клавиатурные паттерны управления, корректное масштабирование, осмысленное пустое состояние главного экрана, сохранение состояния представления между сеансами.
- Поднимается CI (GitHub Actions) со сборкой артефактов под Windows (.exe), macOS (Intel/Apple Silicon/универсальная), deb и tar.gz.

Изменений spec-уровня нет: весь скелет реализует уже существующие требования `desktop-platform` и `ui-shell` из базовой спеки. Change объявлен `skip_specs: true`.

## Capabilities

### New Capabilities

Отсутствуют.

### Modified Capabilities

Отсутствуют — поведение уже специфицировано:

- `desktop-platform`: реализуются требования «Полностью локальная работа», «Сохранность данных при сбоях» (миграции, WAL, бэкап), «Одиночный экземпляр приложения», «Кросс-платформенные сборки».
- `ui-shell`: реализуются требования «Светлая и тёмная темы», «Клавиатурное управление», «Корректное масштабирование», «Осмысленные пустые состояния», «Сохранение состояния представления».

Требования «Контраст текста» (WCAG AA) и «Индикация длительных операций» будут закрыты в этом же этапе по мере появления реальных экранов; их поведение уже описано спекой и не меняется.

## Impact

- Новый код: корень приложения (main/renderer/shared/utility), инфраструктура БД, CI-workflow. Существующего кода нет — конфликтов не может быть.
- Технологический стек фиксируется в design.md (Electron, React, SQLite, ORM, сборщик) — это решение принимается один раз и станет основой всех последующих change.
- Задаёт структуру каталогов и паттерны (IPC, Repository, миграции), которым будут следовать все доменные этапы.
