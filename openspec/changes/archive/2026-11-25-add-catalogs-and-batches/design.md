# Design

## Context

Скелет готов и заархивирован: Electron-каркас, тонкий preload-транспорт, zod-валидация на обеих границах IPC, SQLite + Drizzle (WAL, миграции, автобэкапы), темы, SingleInstance, utility process. Реализуемые требования: `reference-catalogs` (3), `application-settings` (2), `batch-management` (9) — из базовой спеки, поведение не меняется.

## Goals / Non-Goals

**Goals:**
- Доменный слой данных и CRUD-интерфейсы, на которые этап 3 (замеры) наложится без переделок.
- Придерживаться зафиксированных паттернов скелета: Repository над drizzle, zod-дескрипторы каналов в `shared/`, конверт `{ok, data|error}`, UTC-метки, диjest-диалоги.

**Non-Goals:**
- Замеры, приборная коррекция (температурная, Террилла), расчёты брожения (ABV, остаточный сахар, прогноз), график, журнал — этапы 3–4. Однократный перевод Brix→SG при сохранении старта — в этом change (см. D7).
- Встроенный справочник дрожжей производителя — только пользовательский.
- Редактирование истории статусов задним числом — переходы только append-only от текущего.

## Decisions

### D1. Схема БД: нормальные таблицы, JSON — только для добавок-«прочего»

- `instruments`: `id` (uuid text PK), `name`, `type` (`refractometer-atc | refractometer | hydrometer | other`), `wcf` (REAL nullable — рефрактометр), `calibrationOffsetSg` (REAL nullable — ареометр), `createdAtUtc`, `updatedAtUtc`. Калибровочная пара «рефрактометр—ареометр» появится в этапе коррекции; сейчас поля из спеки `reference-catalogs` (ATC, WCF, смещение).
- `yeastStrains`: `id`, `name`, `producer`, `tempMinC`/`tempMaxC` (nullable), `alcoholTolerancePct` (nullable), `notes`, метки.
- `batches`: `id`, `title`, `rawMaterial` (сорт/сырьё), `style`, `volumeLiters` (nullable), `startDateUtc`, `status` (текстовый enum), стартовые параметры одним JSON-столбцом `startParams` (`{gravity: {raw: {value, unit: 'sg'|'brix', instrumentId?}, ogSg}, ph?, tempC?}` — сырое показание и вычисленный OG в SG хранятся рядом (req 1.5), параметры фиксируются разом и читаются целиком; отдельные столбцы дали бы ширину без пользы), итоговые характеристики JSON-столбцом `finalResult` (финальная плотность, крепость, органолептика — заполняется при архивации), `createdAtUtc`, `archivedAtUtc?`.
- `batchYeast`: `id`, `batchId` FK → batches ON DELETE CASCADE, `strainId` (nullable FK → yeastStrains ON DELETE SET NULL — штамм можно удалить из справочника, не теряя запись в партии), `strainName`, `producer`, `doseAmount`, `doseUnit` (`g | ml | packet`), `addedAtUtc`, `productionDateUtc?`.
- `batchAdditions`: `id`, `batchId` FK CASCADE, `name`, `kind` (`nutrient | enzyme | so2 | sugar | acid | other`), `doseAmount`, `doseUnit` (free text), `addedAtUtc`, `notes?`.
- `batchStatusHistory`: `id`, `batchId` FK CASCADE, `fromStatus` (nullable — постановка), `toStatus`, `atUtc`. Append-only.

*Альтернатива*: стартовые параметры/итоги отдельными столбцами — отклонено: читаются только целиком в карточке, дрейф схемы при добавлении полей (позже: инструмент замера) дешевле в JSON. Дрожжи/добавки — таблицами: по ним будут выборки этапа 3 (последний штамм как дефолт).

### D2. Статусы: строковый enum в TS + валидация zod, без CHECK в SQL

`'fermenting' | 'slow-fermenting' | 'aging' | 'bottling' | 'archived'`. Правила переходов: полный граф разрешён (спека: «позволять переводить между статусами» без ограничений графа), архивация — отдельная операция, требующая `finalResult` и пишущая `archivedAtUtc`. Валидация на границе IPC zod-схемой; SQLite хранит текст.

### D3. Репозитории: InstrumentRepository, YeastStrainRepository, BatchRepository

Тонкие классы над drizzle, как AppStateRepository. BatchRepository инкапсулирует транзакцию «создать партию + дрожжи + добавки + запись истории постановки» и «сменить статус (+history)». `markDirty` бэкап-планировщика — на каждую мутацию. Юнит-тесты на in-memory SQLite с реальными миграциями (как тест миграций скелета).

### D4. IPC: каналы-дескрипторы по существующему образцу

Новые каналы в `src/shared/ipc/contracts.ts`: `instruments:list/create/update/delete`, `yeast-strains:list/create/update/delete`, `batches:list/list-archived/create/get/update-status/archive/update/delete`, `settings:get/set`. Ответы списков — массивы записей; удаление возвращает `{ok}` либо ошибку `IN_USE`, если прибор ещё понадобится замерам (этап 3) — пока удаляем безусловно, но код ошибки уже заложен. `settings` хранит один ключ `settings` в `app_state` (`{densityUnit: 'sg'|'brix', correctionFormula: 'terrill'|'linear'}`) — переиспользует инфраструктуру скелета и бэкапы.

### D5. Renderer: навигация табами, доменные сторы

- Шапка с тремя табами: «Партии», «Справочники», «Настройки»; переключение Tab/стрелками (roving tabindex), хоткеи `Mod+1/2/3` в реестре хоткеев. Активный таб сохраняется в `app_state` (требование «Сохранение состояния представления»).
- Сторы: `catalogs-store`, `settings-store`, `batches-store` (zustand, по образцу app-store), данные через типизированный `api`-клиент (расширяется новыми методами).
- Формы CRUD: нативные контролы, `Enter` — сохранить, `Esc` — отмена; ошибки валидации zod показываются текстом у поля (требование «понятное сообщение об ошибке»).
- Подсказка при первом добавлении прибора (спека `reference-catalogs`): после добавления первого прибора раскрываемый блок «зачем температура сусла/калибровочная пара».
- Карточка партии: форма создания (все поля спеки), затем панель статусов с кнопкой текущего перехода, секции дрожжей/добавок (добавление списком), архивация — диалог с полями итога, удаление — диалог подтверждения.

### D6. Пустое состояние главного экрана становится функциональным

Кнопка «Новая партия» активируется и открывает форму создания; когда партий нет, список партий и есть пустое состояние («Поставьте первую партию»).

### D7. Стартовая плотность: OG всегда хранится в SG

Индустриальная конвенция и vision (req 1.5–1.6): OG — в SG, потому что все формулы расчётов работают в SG; сырое показание в Brix хранится рядом как исходное. При сохранении партии вычисление происходит один раз и результат фиксируется:

- введено Brix (рефрактометр) → применяется WCF прибора (если задан; иначе 1.0) → `ogSg = brixToSg(brix_скорректированный)` по формуле из «Специфики предметной области» vision;
- введено SG (ареометр) → применяется калибровочное смещение прибора (если задано) → `ogSg`.

Чистая функция `brixToSg` — в `src/shared/calculations/density.ts`, юнит-тесты на контрольных примерах формулы и граничных значениях (чистые функции тестируются без Electron — требование vision). Вычисление выполняется в транзакции создания партии (BatchRepository) — единственное место записи старта. Форма замера показывает вычисленный OG рядом с сырым вводом ещё до сохранения (мгновенный предпросмотр). Температурная коррекция ареометра и коррекция Террилла остаются в этапе 3 (`measurement-correction`): температура старта сохраняется, но к пересчёту OG здесь не применяется.

## Risks / Trade-offs

- [«Текущая плотность» в списке партий не реализуема до этапа 3] → в списке «—»; в карточке видно, что замеров нет. Полное поведение списка закрывается этапом измерений; отступление зафиксировано здесь и в proposal, спека не меняется.
- [JSON-столбцы слабее типизируются на уровне БД] → zod-схемы `startParams`/`finalResult` в `shared/` валидируют на границе; drizzle `mode: 'json'` даёт TS-тип.
- [Полный граф переходов статусов позволяет бессмыслицу («Архив» → «Брожение»)] → спека требует свободы переходов; осмысленность контролирует пользователь. Если на практике понадобится — отдельный change с MODIFIED-требованием.
- [Формула Brix→SG на невалидном вводе даёт бессмысленный OG] → zod-граница: 0–80 °Bx и физический диапазон SG; предпросмотр OG в форме до сохранения делает ошибку видимой сразу.
- [Рост площади IPC (19 каналов) при копипасте] → фабрика CRUD-дескрипторов в contracts (один генератор для list/create/update/delete трёх сущностей), чтобы дескрипторы не расходились.

## Migration Plan

Одна новая миграция drizzle (добавление 5 таблиц), применяется при старте штатным механизмом; защитный бэкап создаётся автоматически перед миграцией (скелет). Откат на уровне кода — не требуется (релизов не было).

## Open Questions

- Точный состав полей «итоговых характеристик» при архивации (кроме финальной плотности, крепости, органолептики из спеки) — уточнится на практике, JSON-столбец расширяется без миграции.
