# Design

## Context

Мотивация — в proposal.md. Состояние на сегодня:

- Тексты зашиты в код тремя слоями:
  - литералы JSX и карты подписей в renderer (`App`, экраны, `ui/composition`, `help/glossary`; карты `STATUS_LABELS`, `OPERATION_KIND_LABELS`, `INSTRUMENT_TYPE_LABELS`, `KIND_LABELS`, `ADDITION_KIND_LABELS`);
  - сообщения, которые рождаются в main и shared и приходят в renderer на лету: сообщения zod в `ipc/contracts.ts`, сообщения прогноза в `calculations/analysis.ts`, заголовок диалога экспорта в `ipc/register.ts`, ошибки `throw new Error` в репозиториях;
  - готовые фразы, которые `calculations/pipeline.ts` пишет в `measurements.corrections` (примечания шагов, `warnings`, `infos`).
- Ошибка IPC показывается пользователю как есть: `client.ts` бросает `new Error("[CODE] message")`, экраны выводят `e.message`. Сегодня это смесь языков: `Batch is already archived` рядом с `Штамм не найден в справочнике`.
- `pipeline.ts` — чистая функция; renderer вызывает её напрямую для предпросмотра, main — при сохранении замера.
- Настройки — один JSON-ключ `settings` в `app_state`. `settings:get` прогоняет сохранённое через `settingsSchema.safeParse` и при неудаче отдаёт дефолт; форма настроек отправляет весь объект целиком при любом изменении.
- Дефолтное меню Electron 45 всегда английское: при `--lang=ru` остаются «File», «Edit», «Copy».
- Ограничения: строгое CSP без `'unsafe-eval'`, работа без сети (desktop-platform), тесты в окружении node (vitest), `strict` и `noUncheckedIndexedAccess`.

## Goals / Non-Goals

**Goals:**

- Один источник текстов для main, renderer и тестов; новый язык — файл каталога и одна строка реестра.
- Смена языка меняет всё, что видит пользователь, включая сообщения main и след сохранённых замеров.
- Полнота каталога гарантируется тестами, а не вниманием.
- Кроме языка ничего не меняется: формулы, числа, даты и данные пользователя остаются прежними.

**Non-Goals:**

- Типобезопасность ключей на этапе компиляции (см. D7).
- Локализация форматов чисел и дат, ICU-сообщения.
- Перевод пользовательских данных, комментариев, спек и `docs/`.
- Перенос существующих записей следа на машинные коды.

## Decisions

**D1. i18next + react-i18next.** Решение пользователя: приложение open-source, и каталог должен быть готов к сторонним переводам. JSON-каталог i18next понимают платформы перевода (Crowdin, Weblate) без конвертации; склонения i18next берёт из `Intl.PluralRules`; одна и та же библиотека работает и в Node (main), и в React (renderer). Альтернативы: типизированные словари на TS (ключи проверяет компилятор, ноль зависимостей) — отвергнуты, потому что неудобны для сторонних переводчиков; Lingui и Format.JS (ICU, более тяжёлая сборка) — не нужны для русского и английского. Цена выбора: ключи JSON не проверяет компилятор; компенсируется в D7.

**D2. Каталог: `src/shared/i18n/locales/<lang>/translation.json`, одно пространство имён, вложенные разделы по экрану или домену.** Ключи вида `tabs.batches`, `batch.status.fermenting`, `trace.hydrometerTemp`, `menu.copy`. Русский — язык-источник: новая фраза сначала пишется в `ru`, затем в `en`; тест паритета не даст им разойтись. Альтернатива — пространство имён на каждый экран: больше файлов и настройки без выгоды при нескольких сотнях ключей.

**D3. Два экземпляра i18next из одного модуля `src/shared/i18n/`.** Main и renderer — разные процессы с изолированным контекстом, общий экземпляр невозможен. Оба создают экземпляр одной фабрикой `createI18n(lng)` с одинаковыми ресурсами и настройками; renderer дополнительно подключает `initReactI18next`. Main нужен каталог для меню, заголовка диалога экспорта и текста следа при сохранении. Альтернатива «main без текстов, renderer передаёт готовые строки» отвергнута: текст следа рождается на сервере из расчёта, и доверять его renderer'у нельзя. Preload остаётся без зависимостей (sandbox): пользовательских текстов в нём нет.

**D4. Язык: `language: 'system' | <код языка>`; эффективный язык вычисляет main.** `resolveLanguage(setting, app.getLocale())`: для `'system'` — русский, если базовый язык системы `ru`, иначе английский; для явного выбора — выбранный код, если он поддерживается, иначе английский. `settings:get` возвращает `{ settings, resolvedLanguage }`, `settings:set` — `{ ok, resolvedLanguage }`. Renderer инициализирует i18n и `document.documentElement.lang` по `resolvedLanguage` до первой отрисовки, без вспышки на другом языке.

Почему хранится `'system'`, а не вычисленный язык: форма настроек отправляет весь объект при любом изменении. Если бы `get` возвращал вычисленный язык, первое же изменение другой настройки закрепило бы его. Хранение `'system'` сохраняет следование системе до явного выбора. Альтернатива — вычислить язык один раз при первом запуске и сохранить — теряет следование системе.

**D5. Мгновенное переключение — через `useTranslation()`, без перемонтирования приложения.** Все тексты берутся из `t` в момент отрисовки; карты подписей в сторах заменяются вызовами `t` по коду, сторы текстов не хранят. Глоссарий и формулы переезжают из `help/glossary.ts` в каталог; в коде остаются списки идентификаторов (`GLOSSARY_ORDER`, выражения формул). Альтернатива — перемонтировать корень по ключу языка: сбрасывает локальное состояние компонентов (открытые формы) без необходимости.

**D6. След: pipeline выдаёт код и параметры, текст рендерится при сохранении, хранение аддитивное.**

```
  pipeline.ts (pure, language-free)
    steps:     [{ type, input, output, code, params }]
    warnings:  [{ code, params }]
    infos:     [{ code, params }]
        |                                   |
        | renderer: live preview            | main: save measurement
        v                                   v
  t(code, params)                    text = i18n.t(code, params)
                                      stored in measurements.corrections:
                                        steps: [..., note: text]
                                        warnings, infos: text[]        (as before)
                                        warningCodes, infoCodes: refs  (new)
                                            |
                                            v
                                renderer: code ? t(code, params) : note
```

Pipeline остаётся чистым и независимым от языка: тесты проверяют коды и параметры, а не формулировки. Текст сообщений пишется в main при сохранении на действующем языке — для чтения экспорта без приложения (data-portability). Новые поля опциональны, поэтому записи без кодов валидны без миграции; интерфейс показывает их по сохранённому тексту. Поле `type` шага остаётся классификацией шага и код не заменяет: один `type` (`fermentation-correction`, `novotny-model`) покрывает примечания с разным смыслом.

Альтернатива — не хранить текст, а восстанавливать его при экспорте — отвергнута: для этого пришлось бы заново прогонять расчёт по прибору, параметры которого могли измениться, а след обязан отражать то, что применено на самом деле.

**D7. Гарантии каталога — тестами.** `tests/i18n-catalog.test.ts`:

1. Множества базовых ключей всех языков совпадают с русским.
2. Нет пустых строк.
3. Каждый литеральный ключ `t('…')` в `src` есть в каждом языке.
4. Динамические семейства ключей полны: для каждого кода статуса, типа операции, типа прибора, вида замера, вида добавки, единицы дозы, идентификатора глоссария и каждого кода следа, который выдаёт pipeline в своих тестах.

Для склонений базовым считается ключ без суффикса категории (`_one`, `_few`, `_many`, `_other`); дополнительно требуются все формы категорий данного языка. Поэтому имена ключей не должны заканчиваться суффиксом категории, если это не склонение.

Почему не типы: TypeScript выводит из JSON-импорта `string`, а типобезопасность потребовала бы генерации типов или TS-модулей вместо JSON. Альтернатива — `i18next-parser`: лишняя зависимость и настройка, при примерно сорока файлах хватает сканирования.

**D8. Сообщения main — кодами.** Доменные сообщения zod в `contracts.ts` становятся ключами каталога. Конверт ошибки получает `key`, `params` и список `issues` (`path`, `key`): renderer переводит по ключу, а для встроенных ошибок zod без ключа показывает общее сообщение о проверке полей. Ошибки домена в репозиториях бросаются как `AppError(code, params)` вместо текста. Нестандартные исходы прогноза получают `reason` (`minPoints`, `minSpan`, `notDeclining`) вместо готовой фразы. `client.ts` бросает `IpcError` с этими полями; экраны показывают `describeError(e, t)` вместо `e.message`.

`formatAbv` принимает `t`: `{{value}} % об.` в русском, `{{value}} % ABV` в английском. `formatDensity` не меняется: SG и °Bx не зависят от языка.

Обозначения единиц вида «% об.» — часть локализации (решение пользователя): они переводятся вместе с каталогом и зависят от языка интерфейса, а числовое значение и физические единицы (SG, °Bx, °C) — нет. Правило зафиксировано дельтой «Единый формат крепости» в `fermentation-calculations` и сценарием «Обозначения единиц как локализация» в `localization`.

Альтернатива — переводить сообщения main по тексту — отвергнута: любая правка формулировки тихо ломала бы перевод.

**D9. Меню описывается в коде (`src/main/menu.ts`) и пересобирается при смене языка.** Состав пунктов повторяет дефолтное меню, кроме Reload и Force Reload; Toggle Developer Tools остаётся для диагностики. Пунктам-ролям задаются переведённые подписи: собственные подписи ролей в Electron всегда английские. Горячие клавиши сохраняются за счёт ролей.

**D10. Формат чисел в сообщениях не зависит от локали.** Интерполяция печатает числа как есть; точность задаётся именованным форматом (`{{r, fixed2}}`), общим для обоих экземпляров. Десятичный разделитель остаётся точкой, даты — ISO, как сейчас. `Intl.NumberFormat` не используется: показания приборов вводятся числами, и смена разделителя сломала бы ожидания.

**D11. Ресурсы зашиты в сборку, без загрузки в рантайме.** JSON импортируется статически и попадает в бандлы main и renderer (`resolveJsonModule` в обоих tsconfig). Никаких backend-плагинов i18next: так требуют офлайн-работа и CSP `default-src 'self'`. i18next не компилирует сообщения через `eval`, так что `script-src 'self'` остаётся без `'unsafe-eval'`; проверяется первым шагом реализации.

**D12. Список языков — из реестра каталогов.** `src/shared/i18n/locales.ts` импортирует каталоги и перечисляет их в одном объекте: новый язык — файл каталога и одна строка в реестре; экраны не меняются, коды языков и подписи выбора берутся из реестра. Альтернатива — автообнаружение через `import.meta.glob` — отвергнута: в main-процессе ради одной строки пришлось бы настраивать сборку и типы.

**D13. Резервный язык — английский.** Если в текущем языке нет ключа, показывается английский текст, а не служебный идентификатор. Английский понятнее русскоязычного для большинства пользователей; тест паритета делает резервный язык страховкой, а не штатным путём.

**D15. README, LICENSE, package.json.** README.md и README_ru.md зеркальны по структуре: название и одна фраза о приложении, ссылка на второй язык, скриншот, для кого приложение, возможности по текущему реализованному составу, обращение с данными (локально, без сети, экспорт JSON, резервные копии), установка из GitHub Releases по платформам. Только продуктовое описание: без раздела для разработчиков, инструкции по переводу и заметки о macOS. LICENSE — текст MIT; GitHub определяет лицензию по файлу, дополнительно задаётся поле `license` в `package.json`.

## Risks / Trade-offs

- [Английские строки длиннее русских на 10–20 %] → проверка обоих языков в собранном приложении при минимальной ширине окна (640): кнопки и вкладки на перенос и обрезание.
- [Ключи JSON не проверяет компилятор] → тесты из D7 в CI.
- [Старые замеры показывают след на языке записи] → так решено для записей без кодов; затронут только существующий пользователь.
- [Текст следа хранится дважды — кодами и готовой строкой] → небольшой рост объёма записи; цена читаемости экспорта.
- [Встроенные сообщения zod остаются английской прозой] → для них показывается общее локализованное сообщение; доменные проверки имеют собственные ключи.
- [Значения крепости хранятся числами] → перевод обозначения «% об.» / «% ABV» затрагивает только интерфейс и сохраняемые тексты следа (на языке записи); само значение от языка не зависит.
- [Другие спеки цитируют русские подписи и обозначения в сценариях (ui-shell, measurements, batch-management, application-settings; «% об.» и «г/л» в примерах ввода в reference-catalogs и batch-management)] → цитаты считаются подписями на языке-источнике и не переписываются; общие требования — в `localization` и в дельте `fermentation-calculations`.
- [Меню пересобирается в рантайме] → `Menu.setApplicationMenu` поддерживается на всех платформах; сочетания клавиш сохраняют роли.

## Migration Plan

- Миграция базы не нужна: `language` получает значение по умолчанию, поля следа опциональны.
- Порядок: ветка `feature/add-localization` → PR → CI → слияние. Существующие замеры читаются по сохранённому тексту.
- Откат: достаточно отменить коммит — записи с кодами остаются валидными для старого кода, новые поля отбрасываются при разборе ответа.
